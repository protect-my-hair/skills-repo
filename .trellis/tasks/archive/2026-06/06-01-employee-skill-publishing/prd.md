# 员工发布与管理 Skills

## 目标

在现有内部 Skills 管理平台上扩展员工侧能力：员工不仅可以浏览公共
Skills 仓库，还可以创建 Skill、发布到自己的个人发布面板，并管理自己
发布的 Skills。员工个人发布内容进入公司公共 Skills 仓库前，必须经过
管理员审核。

## 背景

现有 MVP 已经覆盖员工浏览公共 Skills、追踪版本，以及管理员创建、导入、
编辑、发布、下架和批量管理 Skills。当前新需求的重点是把员工从“使用者”
扩展为“创作者”，但不把员工直接提升为平台管理员。

因此本需求需要补齐三条能力：

- 员工创建 Skill。
- 员工发布和管理自己的 Skills。
- 管理员审核员工提交的 Skills，并决定是否进入公共仓库。

## 已确认决策

- 员工可以创建 Skill 草稿。
- 员工可以把自己的 Skill 发布到个人发布面板。
- 员工发布的 Skill 在审核通过前不会自动进入公司公共 Skills 仓库。
- 员工个人发布区的 Skill 进入公共仓库前需要审核。
- MVP 审核流程采用管理员单人审核：员工提交审核，管理员通过或驳回。
- 管理员审核通过后，Skill 才进入公司公共仓库并对其他员工可见。
- 现有员工浏览公共 Skills 仓库的体验继续保留。
- 新增“我的发布 Skills”面板，员工可以查看和管理自己发布的 Skills。
- MVP 员工管理动作限定为查看、编辑、撤回/下架、提交公共仓库审核。
- MVP 员工创建入口同时支持手动创建和受控内部 Git 导入。
- 员工发布的 Skill 在管理员审批前仅创建者本人可见。
- 员工创建 Skill 使用现有完整字段集，不做简化表单。
- 技术建模上应使用独立的发布范围或可见性字段区分个人发布与公共仓库发布，
  现有状态字段继续表达生命周期状态。
- 涉及前端页面设计时，必须优先使用用户指定的 `ui-ux-pro-max` 技能。

## 用户角色

- 员工：浏览公共 Skills 仓库，创建自己的 Skill，发布到个人面板，维护自己
  发布的 Skill，并提交公共仓库审核。
- 管理员：保留现有管理能力，并新增审核员工提交 Skills 的能力。

## 产品信息架构

员工侧需要区分两个区域：

- Skills 仓库：现有公共仓库浏览体验，只展示公司公共可见的 Skills。
- 我的发布 Skills：新增员工个人管理面板，只展示当前员工创建、个人发布、
  待审核、被驳回或已撤回的 Skills。

推荐的 UI 结构：

- 在现有控制台中增加清晰入口，例如顶部 Tab 或侧边导航。
- `Skills 仓库` 用于浏览、搜索、筛选公共 Skills。
- `我的发布` 用于创建、导入、编辑、撤回、提交审核员工自己的 Skills。
- 管理员保留现有管理入口，并新增审核队列入口处理员工提交。

前端页面设计阶段要求：

- 优先使用 `ui-ux-pro-max` 技能完成页面设计。
- 如果当前执行环境仍未提供该技能，需要先向用户说明，再由用户确认是否使用
  可用的替代设计流程。

## 功能需求

### 员工创建 Skill

员工可以通过两个入口创建 Skill：

- 手动创建：在产品 UI 中填写 Skill 元数据和内容。
- 受控内部 Git 导入：从批准的内部 Git 来源导入元数据和内容。

受控 Git 导入只做可信来源的元数据和内容导入，不支持任意远程 URL，不执行
导入代码，不做后台仓库扫描。

员工创建 Skill 时需要填写与现有管理员创建流程一致的完整字段：

- Skill 名称。
- 描述。
- 分类。
- 标签。
- 兼容工具。
- 维护团队。
- 维护者。
- 安装方式。
- 依赖说明。
- README 或用法内容。
- 版本号。
- 变更说明。

### 我的发布 Skills 面板

员工可以在“我的发布 Skills”面板中看到自己创建或发布的 Skills，包括：

- 草稿。
- 已发布到个人面板但未提交审核的 Skills。
- 已提交审核的 Skills。
- 被管理员驳回的 Skills。
- 员工已撤回或下架的 Skills。

MVP 支持的员工管理动作：

- 查看详情。
- 编辑内容和元数据。
- 撤回或下架个人发布的 Skill。
- 提交审核，请求进入公共 Skills 仓库。

版本管理、协作者管理和 ownership 转交流程不进入本次 MVP。

### 个人发布与公共仓库审核

员工发布 Skill 后，该 Skill 只进入员工自己的“我的发布 Skills”面板。审核
通过前，其他员工在公共 Skills 仓库中不可见。

员工可以把个人发布的 Skill 提交公共仓库审核。管理员审核时可以：

- 通过：Skill 进入公共 Skills 仓库，对其他员工可见。
- 驳回：Skill 保持在员工个人面板，不进入公共仓库，并展示清晰驳回原因。

MVP 不做多人审核、团队维护者审核、分类路由审核。

### 管理员审核入口

管理员需要能看到员工提交的待审核 Skills，并对每个提交执行通过或驳回。

审核列表至少需要展示：

- Skill 名称和描述。
- 创建者。
- 分类和兼容工具。
- 提交时间。
- 当前状态。
- README 或内容预览入口。

管理员驳回时需要填写原因，员工在“我的发布 Skills”面板中可以看到该原因。

## 权限与可见性规则

- 员工只能管理自己创建或发布的 Skills。
- 员工不能编辑其他员工的个人发布 Skills。
- 员工不能直接把 Skill 发布到公共仓库。
- 员工个人发布的 Skills 在审核通过前仅创建者本人可见。
- 公共 Skills 仓库只展示审核通过且公共可见的 Skills。
- 管理员可以查看审核队列，并通过或驳回员工提交。
- 管理员保留现有对公共 Skills 的管理能力。

## 状态与发布范围模型

生命周期状态和可见性应分开建模：

- `status` 表达生命周期，例如草稿、待审核、已发布、已下架、已归档。
- `scope` 或 `visibility` 表达发布范围，例如个人发布区或公共仓库。

这样可以避免把 `published` 同时解释为“个人已发布”和“公共已发布”。例如：

- 员工 Skill 可以是个人范围内的已发布，但仍不是公共仓库内容。
- 员工提交审核后，生命周期进入待审核。
- 管理员通过后，可见性切换为公共仓库可见。

## 非功能需求

- 保持现有 Skills 仓库浏览体验稳定，不因新增个人面板影响公共仓库筛选。
- 权限判断必须在服务端边界执行，不能只依赖前端隐藏按钮。
- 创建、编辑、提交审核、审核通过、审核驳回、撤回/下架都应记录审计日志。
- 用户可见错误信息需要清晰友好。
- 不在代码、日志、错误信息或测试快照中输出密钥、token、cookie 等敏感信息。
- 实现保持简单，优先复用现有创建、导入、编辑和状态流转能力。

## 验收标准

- 员工登录后可以继续浏览公共 Skills 仓库。
- 员工可以进入“我的发布 Skills”面板。
- 员工可以手动创建 Skill，并填写完整字段。
- 员工可以从受控内部 Git 来源导入 Skill。
- 员工创建或发布的 Skill 在审核通过前只对本人可见。
- 员工可以查看、编辑、撤回/下架自己的 Skill。
- 员工可以提交自己的 Skill 到公共仓库审核。
- 管理员可以看到员工提交的待审核 Skills。
- 管理员可以通过审核，使 Skill 进入公共 Skills 仓库。
- 管理员可以驳回审核，并填写驳回原因。
- 被驳回的 Skill 留在员工个人面板，员工可以看到驳回原因并继续修改。
- 普通员工无法管理其他员工的个人发布 Skills。
- 普通员工无法绕过审核直接发布到公共仓库。
- 相关服务端权限、可见性过滤、状态流转和审核逻辑有测试覆盖。

## 暂不纳入本次范围

- 多人审批流。
- 团队或分类维护者路由审核。
- 员工侧版本管理。
- 协作者管理。
- ownership 转交。
- 未审核 Skill 的团队可见、链接分享或全员可见。
- 真实客户端安装或分发。
- 任意远程 Git 导入。
- 执行导入代码。
- 后台仓库扫描。
- 新增管理员数据分析看板。
