# 登录、注册与登出跳转

## 目标

为 Skills Repo 增加独立的认证入口：

- 用户可以打开登录页面并完成登录。
- 用户可以注册账号。
- 用户登录后进入系统首页。
- 首页右上角的登出按钮点击后，需要清除会话并跳转回登录页面。

当前任务仍处于 PRD 对齐阶段。PRD 未确认前不进入代码实现。

## 用户决策

已选择方案 A：基于 Prisma/PostgreSQL 的真实邮箱密码账号体系。

注册成功后，系统自动为新用户建立登录会话，并跳转到系统首页。

登录/注册页面前端设计使用现有 `ui-ux-pro-max` 方向：延续当前 Skills Repo 的深色 OLED、企业控制台、终端感视觉系统，而不是普通后台表单页或营销落地页。

## 当前仓库事实

- `src/app/page.tsx` 当前直接渲染 `SkillsConsole` 作为根页面。
- `src/components/SkillsConsole.tsx` 已经使用 `next-auth/react` 的 `useSession()`、`signIn()` 和 `signOut()`。
- 当前未登录 UI 嵌在 `SkillsConsole` 内部，并通过 `INTERNAL_AUTH_USERS` 展示内置用户按钮。
- 当前登出逻辑调用 `signOut({ redirect: false })`，只清理本地组件状态，不会跳转到独立登录页面。
- `src/auth.ts` 已配置 Auth.js / NextAuth credentials provider，但当前 provider 只接收邮箱，并从硬编码内置用户中解析用户。
- `prisma/schema.prisma` 已有 Auth.js 兼容的 `User`、`Account`、`Session` 和 `VerificationToken` 模型，但还没有用于自助注册的密码哈希或凭据密钥模型。
- 现有后端 API 路由已经通过 `getActorFromSession()` 解析当前 session 用户。

## 当前文档调研结论

Auth.js 当前文档支持：

- 通过 `pages.signIn` 配置自定义登录页。
- 通过 credentials provider 的 `authorize()` 承接应用自己的凭据校验逻辑。
- 通过 `SessionProvider` 和 `useSession()` 在客户端读取会话状态。
- 通过 `signIn()` 和 `signOut()` 的 redirect 选项控制登录、登出跳转行为。

Next.js App Router 当前文档支持：

- 在 Server Components、Server Functions 和 Route Handlers 中使用 `redirect()` 做服务端跳转。
- Route Handler 可使用框架认证失败处理能力；本项目 API 路由仍优先沿用现有 JSON 错误响应约定。

## 产品范围

### 范围内

- 新增独立 `/login` 页面。
- 在认证入口提供登录和注册两个流程。
- 已登录用户访问 `/login` 时跳转到系统首页。
- 未登录用户访问系统首页时跳转到 `/login`。
- 移除或替换 `SkillsConsole` 内部现有的未登录账号选择 UI。
- 更新现有登出按钮，使其清除 session 后跳转到 `/login`。
- 保持基于 session 的 admin / employee RBAC 行为。
- 保留 seeded admin / employee 账号，服务本地开发和测试。
- 为认证映射、注册校验、登录边界和登出跳转补充适合现有测试体系的测试。

### 范围外

- 企业 SSO/OIDC 接入。
- 密码找回、邮箱验证、MFA、邀请制注册、账号锁定和管理员用户管理页面。
- 除认证入口集成所必需内容外，不调整 Skills CRUD、版本管理、Git 导入、审计或权限业务。
- 不替换 Auth.js / NextAuth 技术方案。

## 方案选项

### 方案 A：生产导向的邮箱密码账号体系（已选择）

在现有 Auth.js credentials provider 基础上，增加一方邮箱密码注册与登录。注册时创建 `User` 和凭据密钥记录，并落到 Prisma/PostgreSQL。自注册用户默认角色为 `employee`；seeded admin 继续用于本地管理和测试。

优点：

- 最符合“登录 + 注册”的真实需求。
- 能沿用现有 Auth.js + Prisma 基础。
- 认证逻辑留在 provider 边界内，后续仍可替换为 SSO/OIDC。
- 不再把硬编码内置用户当成长期账号模型。

缺点：

- 需要增加小规模 schema/migration，用于保存密码凭据。
- 需要谨慎处理密码哈希、输入校验和安全错误提示。
- 注册依赖数据库持久化；除非另行确认，不应为 JSON fallback 再实现一套用户认证存储。

### 方案 B：仅开发态账号选择器 + 注册入口外壳

保留现有内置 credentials provider，只把 UI 改造成 `/login` 页面。注册仅作为轻量申请入口或本地开发账号路径，不创建真实账号。

优点：

- 实现成本最低。
- 对现有后端影响最小。
- 适合短期演示。

缺点：

- 不能真正满足用户注册功能。
- 仍受限于硬编码内置用户。
- 很可能很快需要被替换。

### 方案 C：企业 SSO 优先

以 OAuth/OIDC/SSO 作为主登录路径，注册由外部身份系统承接。

优点：

- 更贴近企业生产身份体系。
- 避免应用自己持有密码。

缺点：

- 配置和外部依赖更多，任务更大。
- 用户当前明确提出产品内登录和注册，本方案对当前任务偏重。

## 推荐方向

本任务实现方案 A，并保持第一版克制：

- 登录页包含“登录”和“注册”两种模式。
- 注册字段包括姓名、邮箱、密码和确认密码。
- 自注册用户默认角色为 `employee`。
- seeded admin 账号继续保留，用于本地管理和测试。
- 密码不得明文存储、记录日志、返回前端或出现在测试快照中。
- 登录与注册失败统一使用安全、泛化的用户提示。
- 为后续 SSO/OIDC provider 替换保留清晰边界，不把当前邮箱密码方案写死为唯一长期身份策略。

## 功能需求

### 登录

- 用户可以访问 `/login`。
- 用户可以输入邮箱和密码。
- 登录成功后创建 Auth.js session，并跳转到 `/`。
- 登录失败时停留在 `/login`，展示泛化错误提示。
- 已登录用户访问 `/login` 时自动跳转到 `/`。

### 注册

- 用户可以在 `/login` 页面切换到注册模式。
- 用户需要填写姓名、邮箱、密码和确认密码。
- 邮箱在唯一性校验前需要标准化。
- 重复邮箱注册需要被拒绝，并展示安全、泛化的错误提示。
- 密码和确认密码必须一致。
- 密码必须满足实现计划中定义的最小策略。
- 注册成功后创建 `employee` 用户，自动登录，并跳转到 `/`。

### 首页访问

- 未登录用户访问 `/` 时应跳转到 `/login`。
- 已登录用户可以看到现有 Skills Repo 控制台。
- 控制台只在认证完成后加载 `/api/skills`。
- 当前用户和角色继续从 session 派生。

### 登出

- 首页右上角登出按钮清除 Auth.js session。
- 登出完成后浏览器跳转到 `/login`。
- 登出过程中不应短暂闪现受限数据。

## 安全要求

- 不在日志、UI、API 响应或测试快照中输出密码、密码哈希、token、cookie 或 `AUTH_SECRET`。
- 注册和登录输入必须在服务端校验。
- 密码哈希策略在实现计划中明确，优先使用平台原生能力或经确认的必要依赖。
- 密码凭据数据应与公开 session/read-model 数据隔离，确保不会被应用读模型返回。
- 认证失败提示应泛化，避免泄露账号是否存在。
- 保持服务端 RBAC 为权限边界；前端按钮显隐不作为授权依据。

## 体验要求

- 未登录用户第一屏应是登录/注册页，不是管理控制台。
- 页面视觉应使用 `ui-ux-pro-max` 设计方向，延续现有深色 OLED、企业控制台、终端感风格。
- 登录/注册表单应简洁、清晰、可访问。
- 登录/注册页应复用 `src/app/globals.css` 中现有设计 token，例如 `--bg`、`--surface`、`--surface-muted`、`--green`、蓝/琥珀/红状态色等。
- 登录/注册页可以使用 CSS 网格、微弱扫描线、代码感信息块或可信状态标签来保持产品识别度，但不要新增营销式 hero、装饰性渐变球或与当前控制台不一致的配色。
- 表单控件应保留 8px 或更小圆角、清晰 focus 状态、暗色原生控件适配和移动端不溢出的布局。
- 首页继续保留右上角身份信息和登出按钮位置。
- 不需要新增营销式落地页。
